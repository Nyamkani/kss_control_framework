# 비영점 명령 데이터 흐름 검증 결과

실행일: 2026-09-21. 실제 Motor·IMU·EKF 실행파일을 단일 기존 Bringup 아래 실행했습니다. 명령 생산자는 별도 프로세스에서 시험 고유 접두사 아래 `/cmd_vel`을 깊이 1로 발행합니다. 실제 `/mecanum`을 사용하는 다른 Application과 충돌하지 않도록 접두사만 분리하며 메시지·상대 Topic 경로는 같습니다.

## 시험 구성

기존 `run_integration.py`의 `Uarts` 가상 터미널·수신 반복·프레임 전송을 재사용했습니다. 응답 생성 부분을 재정의 가능하게 분리하고 `run_motion.py`에서 수신 RPM에 따른 응답만 확장했습니다. 기존 영점 시험의 동작은 유지하며 13개 회귀 항목이 통과했습니다.

- `command_producer.cpp`: 별도 프로세스. 동일한 Publisher를 세 시험 동안 유지합니다. 매 발행 시 `CLOCK_MONOTONIC`에서 생성 시각을 새로 읽고 sequence를 증가시킵니다. 20밀리초 대기 간격으로 3초 동안 각 명령을 발행합니다. 성공한 발행 수와 최초·마지막 생성 시각을 기록하며, 종료 후에는 **0 명령을 발행하지 않고 침묵**합니다.
- `MotionUarts`: 수신한 `m` RPM을 즉시 실제 RPM으로 가정하는 이상적 시험 모델입니다. 각 구간에 `RPM × 4320 / 60 × dt`를 적분하여 Encoder 누적값을 정수로 반환합니다. `z`에는 현재 수신 RPM을 그대로 반환합니다. 초기화 `r`은 Encoder만 초기화합니다.
- UART 순서는 Arduino 1,2,3,4이며 바퀴 순서로는 FL,RL,RR,FR입니다. 반경 0.041m, 회전 지레 길이 0.1975m, 원본 부호 -1을 사용합니다. 받은 RPM에서 계산한 몸체 각속도를 적분해 IMU yaw를 생성하고, 동일 각속도를 gyro-z 프레임으로 보냅니다. 11바이트 WT901C 프레임·검사합·기존 SDK 파서를 통과합니다.
- 기존 Tool 백엔드 관찰 프로그램으로 Wheel·IMU·EKF의 실제 발행값을 읽었습니다. 배열 필드 출력만 추가하여 IMU gyro·yaw도 기록합니다. 필터 함수를 직접 호출하지 않습니다.

이는 이상적 응답을 이용한 IPC·데이터 경로 시험입니다. 모터의 관성·슬립·응답 지연·실측 잡음을 모델링하지 않으며 모터 성능이나 EKF 정확도 검증이 아닙니다. 실제 UART·하드웨어에는 접근하지 않았습니다.

## 명령과 실제 UART 관측

입력 단위는 `(m/s, m/s, rad/s)`, RPM은 **Arduino 1,2,3,4 순서**입니다. 최신 명령 우선이므로 모든 발행마다 UART 명령이 전송될 필요는 없습니다.

| 시험 | cmd_vel (vx, vy, wz) | 실제 비영점 RPM 수신 | 성공 발행 / 비영점 UART 수신 수 | 만료 후 0 RPM 수신(ms) |
|---|---|---|---|---|
| 직진 | (0.12, 0, 0) | [-27.949162, -27.949162, -27.949162, -27.949162] | 145 / 31 | 258.223 |
| 횡이동 | (0, 0.1, 0) | [23.290968, -23.290968, 23.290968, -23.290968] | 143 / 31 | 262.711 |
| 제자리 회전 | (0, 0, 0.4) | [18.399864, 18.399864, -18.399864, -18.399864] | 145 / 31 | 257.242 |

마지막 **성공 발행 명령의 생성 시각**부터 가상 Arduino의 첫 0 RPM 명령 수신 시각까지를 측정했습니다. 생산자는 그 사이 Topic을 삭제하거나 0 명령을 발행하지 않았습니다. 따라서 관측한 0 명령은 기존 Motor 만료 경로의 결과입니다. 측정값이 250밀리초보다 큰 부분은 실행 주기·스케줄링·통신 경로를 포함하며 실시간 상한을 보장하지 않습니다. 시험 판정 범위는 250~600밀리초이며 이는 물리 정지 시간 기준이 아닙니다. 연속 유효 명령 구간 중 불필요한 0 RPM은 없었습니다.

## 가상 Arduino 응답 관측

Encoder는 누적 카운트입니다. 시나리오 사이에 초기화하지 않아 절댓값보다 변화 방향이 의미 있습니다.

| 시험 | 첫 Encoder 응답 | 마지막 Encoder 응답 | 움직임 중 RPM 응답 예시 |
|---|---|---|---|
| 직진 | [-30, -30, -30, -30] | [-6491, -6491, -6491, -6491] | [-27.949162, -27.949162, -27.949162, -27.949162] |
| 횡이동 | [-6522, -6522, -6522, -6522] | [-1137, -11908, -1137, -11908] | [23.290968, -23.290968, 23.290968, -23.290968] |
| 제자리 회전 | [-1066, -11900, -1145, -11979] | [3148, -7686, -5359, -16192] | [18.399864, 18.399864, -18.399864, -18.399864] |

세 시험 모두 예상 RPM 부호, Encoder 변화, 비영점 RPM 조회 응답, Wheel·EKF 주운동축의 양의 속도와 위치/방향 변화, IMU 회전값, 만료 정지 및 정상 종료 검사를 통과했습니다. 소수의 비주운동축 성분은 정수 Encoder 양자화와 서로 다른 조회 시각 등이 포함된 관측값이며 정밀도 판정에 사용하지 않았습니다. 구현 결함은 이번 시험에서 발견하지 못했고 내부 로직을 수정하지 않았습니다.

## 변경 파일 및 재현

변경·추가 파일은 이 디렉터리의 `run_integration.py`, `tool_probe.cpp`, `command_producer.cpp`, `run_motion.py`, 이 문서입니다. Bringup 구성, Motor·IMU·EKF 내부, Arduino 펌웨어, Core는 변경하지 않았습니다.

기존 실행파일과 Tool 관찰 프로그램의 빌드 명령은 `../../bringup/README.md`를 사용합니다. 수정된 `tool_probe.cpp`는 해당 명령으로 다시 컴파일해야 배열 기록이 포함됩니다. 추가 명령 생산자와 시험은 다음과 같이 실행합니다.

```sh
c++ -std=c++17 -O2 -pthread -I kcf/include -I application/mecanum/include application/mecanum/tests/integration/command_producer.cpp /tmp/kcf-mecanum-ekf-build/kcf/libkcf_core.a -o /tmp/mecanum-command-producer
PYTHONDONTWRITEBYTECODE=1 python3 application/mecanum/tests/integration/run_motion.py --build-dir /tmp/kcf-mecanum-ekf-build --probe /tmp/mecanum-tool-probe --producer /tmp/mecanum-command-producer --output-dir /tmp/mecanum-motion-final
```

앞선 통합 검증과 같이 감독 소켓을 사용할 수 있는 일반 프로세스 환경에서 실행했습니다. 최종 원시 기록은 `/tmp/mecanum-motion-final/`에 있고 각 시나리오 JSON에는 명령 생성 시각·발행 수·UART 수신 시각과 값·Encoder/RPM 응답·주기적 Topic 관측값·만료 지연을 포함합니다. 기존 영점 회귀 결과는 `/tmp/mecanum-motion-legacy-regression/`에 있습니다. 커밋·푸시·업로드는 수행하지 않았습니다.
