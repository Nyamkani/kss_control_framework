# R5 — Service Introspection / Dynamic Service Call

```text
Topic:     Endpoint → Type → DynamicTopicReader → SHM
Parameter: Endpoint → Type → DynamicParameterClient → SHM
Service:   Runtime → ServiceInfo → Request/Response TypeDescriptor
                                  → DynamicServiceClient → localhost UDP ServiceServer
Supervisor → child membership → Runtime
Supervisor is NOT in the Service data path.
```

## Public discovery and registration

`ServiceInfo` is a separate fixed, trivially-copyable model in
`kcf/introspection/service_info.hpp`. It exposes registration_id, semantic name,
UDP port/service_id, request/response sizes and stable type IDs, and two diagnostic
compiler type strings. It is not added to EndpointInfo and does not describe
ServiceClient relationships. Service ID 0 remains valid; port 0 is invalid.

The existing overload remains source-compatible:

```cpp
server.Register<Request, Response>(service_id, callback);
```

The named overload is:

```cpp
server.Register<Request, Response>(service_id, "/motor/reset_encoder", callback);
```

Create binds and remembers the localhost port. Register prepares immutable wire
identity, handler metadata and descriptor registration functions. After the worker
starts successfully, Start best-effort registers request/response descriptors with
the existing Runtime Type Registry, then publishes ServiceInfo. Stop joins the
worker, removes entries best-effort and closes the socket. No metadata access occurs
per callback or per received request. Invalid/oversized display names fall back to
`service@<port>:<service_id>`; they do not invalidate an otherwise usable handler.

R3 traits and R4 declaration/layout identity helpers are reused. Undefined/invalid
traits yield wire identity 0. Type registry full/conflict/failure leaves the affected
published request or response type ID at 0; the actual wire identity and Service
remain operational. Dynamic discovery requires both nonzero IDs. Identical types
reuse R3's existing deduplication. Diagnostic names are never decode identities.

ProcessRuntime anchors discovery. Without an active Runtime, ServiceServer still
works but does not publish service discovery metadata. Services started before
Runtime activation are not retroactively discovered; restart their lifecycle to
register them. No client graph, global database or Supervisor relay is introduced.

## Service registry and validation

`IntrospectionClient::ListServices(runtime, services)` returns an all-valid vector
and replaces output only on success. It checks live PID/start_ticks before and
after copying, snapshot identity/version/size, capacity, nonzero registration IDs
and ports, request/response sizes in 1..SERVICE_MAX_PAYLOAD, terminated strings,
unique IDs and unique port/service_id pairs. Every nonzero type ID must resolve to
a valid descriptor of the matching payload size in that Runtime's type snapshot.
Partial IDs are permitted metadata but cannot be used for a Dynamic Call.

The internal logical object is `/kcf_introspection_service_<pid>_<start_ticks>`.
The fixed snapshot holds at most 64 services. It is allocated lazily at the first
registration; a Runtime without services normally returns -ENOENT. After successful
removal of its last entry, a live Runtime has an empty snapshot. Runtime end unlinks
the object. Crash leftovers are rejected by PID/start_ticks validation; R5 adds no
global stale-object cleaner. Invalid runtime arguments return -EINVAL, dead/stale
runtime -ENOENT, invalid metadata -EPROTO; underlying storage errors propagate.

Service discovery uses the R2B/R4 nonblocking creation and polling-only snapshot
publication path, not a shared notification mutex. Observer death can abandon pins;
publication has bounded slot attempts and never waits for observers. On publication
failure the registry is unlinked/abandoned to avoid keeping stale owned entries,
while real handlers continue operating. A later lifecycle registration may recreate
it, but it does not automatically republish other already-running servers. IDs are
not reused within a process generation. Discovery is advisory, not a readiness or
liveness guarantee; Stop and requests can race with an already-copied listing.

## Dynamic client

Include `kcf/dynamic/dynamic_service_client.hpp` and link `kcf_core`:

```cpp
kcf::TypeDescriptor request_type, response_type;
int result = introspection.GetType(runtime, service.request_type_id, request_type);
if (result != 0) return result;
result = introspection.GetType(runtime, service.response_type_id, response_type);
if (result != 0) return result;

kcf::DynamicServiceClient client;
result = client.Open(service.port, service.service_id,
                     request_type, response_type, 200, 2);
if (result != 0) return result;
kcf::DynamicPayload request, response;
request.type_id = request_type.type_id;
request.bytes.resize(request_type.payload_size);
// Caller fills valid native bytes according to the request descriptor.
result = client.Call(request, response);
client.Close();
```

Following R4's actual API, Open takes validated descriptors instead of bare
IDs/sizes. This checks bounds and local layout, and prevents silently accepting a
same-ID/different-layout contract. Both descriptors must be valid/nonzero and fit
the 4096-byte Service payload limit. Open prepares the existing localhost transport;
it does not contact the server or prove availability. Actual handler identity is
validated on Call. No application Request/Response header or compile-time T is
required. R4 DynamicPayload is reused; response.sequence is 0 because this API does
not expose transport request IDs as a data version.

Call rejects request ID mismatch with -EPROTOTYPE and byte-size mismatch with
-EMSGSIZE before sending. Response remains unchanged on all failures. Close is
idempotent. Open on an open client returns -EBUSY; Call after Close returns -EBADF.
Calls are serialized by the existing transport; serialize lifecycle operations
with local calls. No raw unvalidated public Call API is exposed: DynamicServiceClient
is a friend of ServiceClient and uses its existing private CallRaw implementation.

## Wire protocol and handler safety

Service protocol is **version 2**, with a 72-byte native-endian ServiceHeader.
The existing fields are followed by request_type_id, response_type_id,
request_layout_id and response_layout_id. The layout fingerprints use the existing
R4 algorithm; stable type IDs still use R3's canonical-name FNV-1a. These identities
are deterministic compatibility checks, not cryptographic authentication.

Typed Call resolves each Request/Response declaration once per template
specialization and includes its identity. Handler identity is resolved at Register.
Neither uses introspection registries in the call path. Each absent descriptor has
ID/layout 0; legacy undefined pairs communicate as 0/0 without source edits. Mixed
known/unknown typed pairs can communicate when both peers agree. All four identity
fields must match the handler exactly, including zero; a caller cannot invent
nonzero IDs to dynamically invoke an untyped handler. Request size must also match.
Mismatch returns a framework error without invoking the callback. Responses for
known handlers carry their actual expected identities.

Before exposing response bytes, the client verifies localhost source address/port,
protocol, packet kind, service ID, client ID, request ID, exact datagram/payload size,
request and response type/layout identities and framework status. A matching response
with wrong type/layout returns -EPROTOTYPE. Unrelated/malformed envelopes are ignored
within the existing timeout window; response size mismatch returns -EMSGSIZE.
Old protocol packets are ignored and cannot invoke a handler.

The transport implementation, timeout/retry_count meaning, random client_id,
monotonic request_id, one outstanding request and 64-entry duplicate cache remain.
Retries reuse the exact request ID/header/bytes. Duplicate validation now includes
both type and layout IDs as well as payload. Reuse of a cached ID with differing
identity/data is rejected without callback execution. Cache eviction and server
restart still bound duplicate suppression; R5 does not promise durable exactly-once
execution. Timeout does not prove that a side-effecting callback never executed.

## Compatibility and scope

SHM format remains **3** from R4. Service protocol increases **1 → 2**. Rebuild and
restart all participating KCF IPC/Service binaries at the same Framework revision;
no backward-compatibility adapter is provided. Typed APIs and descriptor-free types
remain source-compatible. Existing Action users of Service transport also need the
same revision; Action introspection is not implemented.

The Core validates service/type/layout/size and transports bytes. It does not parse
GUI fields, validate application command ranges, prompt users, trace Service traffic,
implement callback monitoring, or route through Supervisor. Future kcf_tools handles
confirmation policy for side-effecting commands. Local native ABI/endianness and
explicit descriptor accuracy remain application contracts. A stale endpoint can
still denote a replacement with the same service/type contract; there is no server
generation authentication or automatic rediscovery in the call path.

kcf_tool, mecanum, GUI, remote access, JSON and Topic Dynamic Monitor are unchanged
or NOT IMPLEMENTED in this stage.

## Validation

```sh
cmake -S . -B build/r5-clean
cmake --build build/r5-clean -j 4
./build/r5-clean/examples/introspection/kcf_service_introspection_test
```

The test covers named/unnamed Runtime discovery; request/response descriptor chain;
dynamic and typed interoperability; equal-size wrong request and response types;
same-ID wrong layout; callback count unchanged on rejection; legacy undefined pairs;
local input errors; response envelope/source/type/layout/size failures and preserved
output; exact retry identity and timeout; actual-server duplicate cache and changed
payload/type rejection; old protocol rejection; registry capacity overflow; type
registry exhaustion/conflict; registry creation/publication failure; malformed
snapshot validation; Stop/restart cleanup; Runtime SIGKILL stale filtering; and the
full Supervisor membership → Runtime → Service → descriptors → direct Call chain.

A test-only memcpy linker wrapper pauses an observer inside the real ListServices
snapshot copy while its slot is pinned. Service calls succeed while it is paused
and after SIGKILL. No production injection hooks or observer work in the server
callback path are added. Other fixtures force full pins/creation failure to verify
metadata errors do not change actual Service lifecycle outcomes.
